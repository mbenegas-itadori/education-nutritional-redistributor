## 1. Overview

This document describes how to reproduce, from scratch, the results of the
paper starting from the POF 2017–18 (IBGE) microdata and the TACO table
(4th ed., NEPA-UNICAMP). It covers: directory structure, software
dependencies, pipeline execution order, and how to validate that a
reproduction is correct.

## 6. Known issues and audit decisions

### 6.1 ✅ Version ambiguity in script 02 — RESOLVED (session 2026-08-20)

At least two versions existed of the script that builds the Ω matrix:

- **`02_matriz_C_v3.py`** (on Drive, `script/` folder): automatic matching
  via `rapidfuzz.token_set_ratio`, no per-item manual dictionary.
- **`02_matriz_C_FINAL.py`** (found locally, in the author's "scripts →
  validated" folder, not on Drive until this session): rewritten with an
  extensive per-group manual dictionary, motivated by the classification
  audit documented in `diagnostico_classificacao_grupos.md`.

**Resolution, with decisive proof**: we ran `02_matriz_C_FINAL.py`
(outputs suffixed `_test`) and compared the resulting Ω against the
published Table A6 — wide divergence (~40 cells, up to 44 p.p. difference).
That alone did not prove which one was correct. The decisive test was
computing η̂ₙ = Ω_test · μ̂ (the Table 8 formula) using the Ω from
`_FINAL`: it matched **exactly** the 10 already-published η̂ₙ values in
Table 8 — proof that **`02_matriz_C_FINAL.py` is the actual version that
generated the paper's published results**, and that the **printed Table
A6 is out of sync** (likely a stale version, never regenerated after the
classification audit that motivated `_FINAL`).

**Action**: `02_matriz_C_FINAL.py` is the canonical version.
`02_matriz_C_v3.py` should be archived under `script/archive/` with a note
explaining it was superseded by the classification audit (see
`diagnostico_classificacao_grupos.md`). Table A6 of the paper needed to be
regenerated from the `_FINAL` output before submission — see
`referencia_v3.md`, item 14.

### 6.4 Median-labeled-as-mean bug (Figures 1–4) — FIXED

In both Engel-curve scripts (`06_engel_nutricional_FINAL.py`,
`08_engel_grupos_FINAL.py`), the dashed vertical line labeled "median" on
the chart came from `np.average(lnm, weights=pesos_n)` — that is a
weighted mean, not a median. Fixed in both: a new `weighted_median()`
function (sorts values, accumulates weight, cuts at 50%), documented in
each script's own docstring. Both scripts were already correctly weighted
elsewhere (central curve via `bin_loess_boot`, bin-then-weighted-mean) —
only this specific point was wrong.

### 6.5 Lesson on transferring large files through this channel

While assembling the validated repository (§5.1), manually transcribing
`01b_base_analitica_v2.py` (14,300 bytes) via base64 produced silent
corruption **twice in a row, identically** — not chance, but systematic.
The corruption was only caught because `py_compile` failed at two points
(missing brackets) and a UTF-8 decoding check failed at a third point
(pure binary noise for ~300 bytes). The file was only recovered intact
(exact byte count, 14,300) after the author uploaded it directly through
the chat, bypassing transcription.

**Practical rule adopted**: for plain-text files, `textContent` is safe up
to roughly the ~15 KB range (tested, intact). For larger files
(`02_matriz_C_FINAL.py`, 127,918 bytes), manual transcription is not
reliable — asking the author to upload/copy the file directly is safer
than any retransmission attempt. When the file already exists intact
somewhere on Drive, `copy_file` (server-side copy) is always preferable to
any form of retranscription, even for small files — it eliminates the
risk entirely.

### 6.6 ✅ `00_classificacao_v2.py` identified — RESOLVED (session 2026-08-27)

Same pattern as §6.1: three candidate versions found on the author's
machine, needed a decisive test against the real output to disambiguate.

- `00_classificacao_v2_robusto_CORRIGIDO.py` — version with 2 fixes
  documented in its own docstring (FIX 1: description used to come from a
  nonexistent file, producing an empty `desc_map`; FIX 2: `VALOR_TOTAL`
  summed raw `V8000` instead of `V8000_DEFLA × PESO_FINAL`, ending up
  ~16× smaller than the correct national value)
- `00_classificacao_v2_robusto.py` — same version, without the 2 fixes
  above (has exactly the 2 bugs that `_CORRIGIDO` documents having fixed)
- `00_classificacao_v2.py` (no suffix) — entirely different architecture:
  no ground-truth lookup, based on ranges + ~14 manual point corrections
  (despite the docstring claiming "399 point corrections" — does not match
  what's actually in the file) + treats Tobacco as its own group via a
  hardcoded `TABACO_87` set

**Decisive test**: comparison against the real
`classificacao_grupos_v2.parquet` (4,848 products, already on Drive). Two
points settle it:
1. The real file has a `METODO` column — only the two `_robusto*`
   versions produce this column; the suffix-less version does not.
2. `VALOR_TOTAL` summed in the real file = BRL 7.67 billion — only
   consistent with FIX 2 applied (`V8000_DEFLA × PESO_FINAL`, national
   scale); the uncorrected version would come out ~16× smaller.

**On "14.Tobacco" not appearing in the classification**: not a gap.
`00_consumo_quaids_v2.py` already documents that tobacco expenditure comes
entirely from Quadro 21 of `DESPESA_INDIVIDUAL`, not from products in the
collective diary — there is no "tobacco product" to classify in this
file. The suffix-less version, which tries to solve this via `TABACO_87`,
is addressing a problem that does not exist in the pipeline's actual
design.

**Conclusion**: `00_classificacao_v2_robusto_CORRIGIDO.py` is the
canonical version, renamed to `00_classificacao_v2.py` and archived in
`script_validados_replicacao/` (§5.1) — completes all 11 steps of the main
pipeline (plus `config.py`, used only by steps 1–2 — 12 files in the
folder in total).

### Additional note: Quadro 24 confirmed for group 12's budget

Additional investigation (session 2026-08-20) confirmed, via
`00_consumo_quaids_v2.py`, that group 12's **budget** (used in the QUAIDS
estimation) does in fact come from Quadro 24 within
`DESPESA_INDIVIDUAL.txt` — the script's own documentation confirms:
`"Food-related Quadros within DESPESA_INDIVIDUAL: 21→Tobacco,
24→Food Away+Alcohol, 41→Food Away (travel)"`. This differs from the
**nutritional composition** (matrix C/Ω), which cannot come from Quadro 24
because that module does not record quantity — only aggregate monetary
value per meal. Section A1.5 of the paper now explicitly distinguishes
these two sources (fixed in this session).
